## What is true today (checked Nov 16, 2026)

- **5.1 as written does not roll anything.** The roadmap says "re-run the
  workflow while a sync is uploading". `deploy.yml` runs
  `aws cloudformation deploy --no-fail-on-empty-changeset`, so re-running a
  deploy of the commit that is already live is an empty change set: ECS
  starts no new task. A real roll needs either a new image (a `dev` push that
  changes `src/`) or `aws ecs update-service --force-new-deployment`, which
  uses the same rolling settings (`minimumHealthyPercent=100`,
  `maximumPercent=200`, 120 s drain and stop timeout). The runbook already
  allows `--force-new-deployment` (secret rotation).
- The client has no command that compares a local run with the server.
  `GET /v2/runs/{id}/state` returns `size` and `sha256` per run file, and
  `POST /v2/objects/missing` tells whether the workspace has an object
  (objects are content-addressed and checked on upload, so present means the
  bytes match).
- The isolation suite (package 18) runs only against local servers.
- The hosted task connects to RDS as the master user; the server logs
  "row-level security is not enforced for database role" at startup if that
  role has SUPERUSER or BYPASSRLS (Backlog, top entry). Nobody has looked.
- The owner's `agenticml-account` AWS profile exists on the supervisor's
  machine. Only the owner runs AWS commands unless the owner says otherwise
  (as on Nov 12, 2026 for Phase 3).

## `scripts/hosted_check.py`

Python 3.10+, stdlib plus the installed `agenticml` package (reuse its
helpers where they exist: run directory layout, allow-lists, object
references, the HTTP client and User-Agent). Host from `AGENTICML_HOST`
(default `https://app.agenticml.xyz`), store from `AGENTICML_DIR`. Keys are
read only from `AGENTICML_API_KEY` or a `getpass` prompt, never from
arguments, and are never printed (print only the 8-character prefix). Exit
code 0 when every check passes, 1 otherwise. Output is a plain table, one
line per check, plus `--json` for the record.

Subcommands:

1. `make-run [--mb 300] [--files 30] [--steps 2000] [--project launch-check]`
   - Creates one finished local run with the SDK: `--files` artifacts of
     random bytes totalling `--mb` MB (`log_artifact(..., copy=True)`),
     `--steps` metric steps for two metrics, a summary value. Prints the run
     id. Runs from a temporary empty working directory so lineage does not
     snapshot the caller's project.
   - Refuses `--mb` above 1500 (the free daily upload limit is 2 GB).
2. `verify RUN_ID [RUN_ID ...]`
   - For each run: `GET /v2/runs/{id}/state`; every local allow-listed run
     file must exist on the server with the same size and sha256; every
     object the run references (artifacts, media, code snapshot) must be
     reported present by `POST /v2/objects/missing` (batches of at most the
     protocol limit); the server's `remote.status` must equal the local
     status and `remote.fingerprint` must be set.
   - Files the server has that are not local are reported, not failed.
3. `isolation --run RUN_ID_B [--object SHA ...] [--slug-b customer-two]`
   - Uses the current key (workspace A, checked with `/v2/whoami`; refuses if
     `whoami.workspace == slug-b`). Object digests default to those
     referenced by the local copy of `RUN_ID_B`, if present.
   - Probes, each expected to reveal nothing:
     - `GET /v2/runs/{B}/state` → 404
     - `GET /v2/runs/{B}/lineage` → 404
     - `POST /v2/runs/{B}/commit` with an empty, harmless body → 404 (must
       not create anything; if the server answers 2xx, fail loudly)
     - `POST /v2/objects/missing` with B's digests → all listed as missing
     - `GET /w/{slug-b}/` and `GET /api/w/{slug-b}/runs` with the key as a
       Bearer token → 401, 403 or 404, never 200
     - the same two URLs with no credentials → 401, 403, 404 or a redirect
       to `/login`, never 200 with data
   - Read-only towards workspace B: no PUT or append to B's run id.
   - Prints the browser step the owner still does by hand: signed in as
     customer-one's owner, open `/w/customer-two/` and a customer-two run
     URL; both must show "not found".

Before writing the commit probe, check in `src/agenticml/server/` what
`POST /v2/runs/{id}/commit` does for a run id unknown in the caller's
workspace; if any body could create state there, drop that probe and say so.

## Runbook section "Launch checks (Phase 5)"

Plain commands, in order, each with its pass line:

- **5.1**
  1. In terminal 1 (customer-one key):
     `python scripts/hosted_check.py make-run --mb 300`, then
     `agenticml sync --all`.
  2. While it uploads, in terminal 2:
     `aws ecs update-service --cluster agenticml-hosted --service agenticml-hosted --force-new-deployment --profile agenticml-account`,
     then
     `aws ecs wait services-stable --cluster agenticml-hosted --services agenticml-hosted --profile agenticml-account`.
  3. If the sync ends early with an error, run `agenticml sync --all`
     again; that counts as a pass only if `verify` passes afterwards.
  4. Run `python scripts/hosted_check.py verify <RUN_ID>`. Then run
     `aws ecs describe-services ... --query 'services[0].events[:5]'` and
     record two things: that the old task stopped after the new one was
     healthy, and the time of each.
  5. The script lives in the repository. On a training machine without a
     checkout, fetch it from `dev` with `curl`.
- **5.2:** with customer-one's key, run
  `python scripts/hosted_check.py isolation --run <customer-two RUN_ID>`.
  Then do the browser step.
- **5.3:**
  - Create a separate venv and run
    `pip install 'agenticml-lite @ git+https://github.com/agenticML/agenticml-lite@bd0d499'`.
  - Use a separate `AGENTICML_DIR`. Run the smoke script, then
    `agenticml sync --all`.
  - Run `verify` with the 3.0 tool.
- **5.4**
  - Run `aws s3api list-objects-v2 --bucket <ObjectsBucket output> --prefix hosted/ --max-items 3`,
    then `aws s3api head-object` on each key. Each must show
    `"ServerSideEncryption": "AES256"`.
  - Download the `checkpoint` artifact from the dashboard. Its `sha256sum`
    must equal the local file's.
- **5.5**
  - Run
    `aws cloudwatch set-alarm-state --alarm-name agenticml-hosted-alb_5xx --state-value ALARM --state-reason "Phase 5 alarm drill"`.
  - Both addresses must get the email. The alarm returns to OK at its next
    evaluation.
  - If the second address gets nothing, re-subscribe it (step 2.1b).
- **5.6**
  - Run
    `aws logs filter-log-events --log-group-name /ecs/agenticml-hosted --filter-pattern '"row-level security is not enforced"' --max-items 5`.
    Any event means row-level security is bypassed; record it in the
    Backlog entry.
  - CloudWatch keeps 30 days, so a task started within that window has
    logged its startup line.

## Constraints and conventions

- Keys never on the command line, in output or in files; `read -rsp` or
  `getpass`.
- The tool must work against a 3.0 server and must not need `src/` changes.
- `isolation` never writes to the other workspace.
- Keep `make-run` within free limits by default (300 MB of the 2 GB daily
  upload, 5 GB storage).
- Plain short sentences in the runbook, matching its voice.

## Edge cases

- A sync interrupted mid-roll: the client retries per request; a second
  `sync --all` must finish and `verify` must pass. A `verify` failure is a
  launch blocker: record it and open a Backlog entry.
- `verify` on a run that is still running: append files may be longer
  locally; finish the run first (`make-run` produces finished runs).
- The 2.2 client is older than the minimum client version: if the server
  answers 426, record that 5.3 fails and why. Do not change the minimum.
- `isolation` when the local store has no copy of run B: needs `--object`
  digests, or it skips the objects probe and says so.
