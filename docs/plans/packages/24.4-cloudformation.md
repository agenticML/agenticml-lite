# Package 24.4 †: CloudFormation replaces Terraform

Nov 10, 2026 · Supervisor plan · Release 3.0 · Coder: Codex; second review Cursor · Size: M

Source: owner decisions of Nov 10, 2026, replacing the Terraform half of
[package 24.2](24-aws-deployment.md):

- **CloudFormation, not Terraform.** No Terraform state bucket or lock
  table; AWS keeps the stack state.
- **One region:** `us-east-2`, hostname `app.agenticml.xyz`.
- **Deploys run from a GitHub workflow** (manual dispatch, protected
  `hosted` environment, OIDC role).
- **No NAT gateway.** Fargate tasks run in public subnets with a public
  IPv4 address for outbound traffic only; their security group accepts
  traffic only from the load balancer. RDS and EFS stay in private
  subnets. Saves about $28/month (NAT ~$35 minus two task IPv4 addresses).
- **Firebase and open sign-up come later.** The stack must start without
  them (people sign in with passwords from invite links); turning them on
  is a configuration change, not a template change.

The image (`deploy/aws/Dockerfile`, `entrypoint.sh`, `limits.json`,
`requirements-hosted.txt`) and `scripts/hosted_smoke.sh` from 24.1 do not
change.

## Goal

The owner can go from an empty AWS account to `https://app.agenticml.xyz/healthz`
with: one `aws cloudformation deploy` of a small bootstrap stack from a
laptop, a few GitHub environment variables, and one run of the deploy
workflow. Every later image or infrastructure change is the same workflow
run against a reviewed commit. Terraform and its CI job are gone.

## Design

Two stacks in `us-east-2`:

1. **`agenticml-hosted-bootstrap`** (`deploy/aws/cloudformation/bootstrap.yaml`),
   created once by the owner with admin credentials. Contains only what
   the deploy workflow needs to exist before it can run:
   - ECR repository `agenticml/lite-server` (immutable tags, scan on
     push, lifecycle: keep last 30 images). `DeletionPolicy: Retain`.
   - GitHub OIDC provider, created only when the parameter
     `GitHubOidcProviderArn` is empty (an account can hold only one
     provider for `token.actions.githubusercontent.com`; agenticml-server
     may already have created it).
   - **Deploy role** `agenticml-hosted-deploy`, trusted only by
     `repo:agenticML/agenticml-lite:environment:hosted` with audience
     `sts.amazonaws.com`. Permissions: ECR push/describe on the one repo
     (plus `ecr:GetAuthorizationToken` on `*`); CloudFormation change-set
     and describe actions on the stack
     `arn:aws:cloudformation:us-east-2:<acct>:stack/agenticml-hosted/*`
     (`CreateChangeSet`, `DescribeChangeSet`, `ExecuteChangeSet`,
     `DeleteChangeSet`, `DescribeStacks`, `DescribeStackEvents`,
     `GetTemplateSummary`; `ValidateTemplate` needs `*`); `iam:PassRole`
     on the CloudFormation role only, with
     `iam:PassedToService = cloudformation.amazonaws.com`;
     `ecs:DescribeServices` on the service ARN pattern (for the
     post-deploy check). No ECS Exec, no direct ECS/RDS/IAM writes.
   - **CloudFormation role** `agenticml-hosted-cloudformation`, trusted by
     `cloudformation.amazonaws.com` (condition `aws:SourceAccount`). It
     carries the permissions to create and update the main stack's
     resources. Scope it by service (ec2 VPC/subnet/SG/route/endpoint
     actions, elasticloadbalancing, ecs, rds, elasticfilesystem, s3,
     acm, route53 record changes on the one hosted zone, logs,
     cloudwatch, sns, backup, secretsmanager for the RDS-managed secret,
     kms needed by RDS/Backup) and limit IAM to roles named
     `agenticml-hosted-*` other than the deploy and CloudFormation roles
     themselves (`iam:CreateRole`, `DeleteRole`, `GetRole`,
     `PutRolePolicy`, `DeleteRolePolicy`, `GetRolePolicy`,
     `AttachRolePolicy`, `DetachRolePolicy`, `TagRole`, `UntagRole`,
     `UpdateAssumeRolePolicy`, `PassRole`), plus
     `iam:CreateServiceLinkedRole` for the ECS, ELB, RDS and Backup
     service-linked roles. Where an action cannot be scoped to a
     resource, use `*` and say why in a comment. Report as a deviation
     if a working stack needs something broader.
   - Outputs: `DeployRoleArn`, `CloudFormationRoleArn`,
     `EcrRepositoryUri`.

   Why a separate stack: the ECR repository must exist before the first
   image is pushed, and the role CloudFormation uses must not live in the
   stack it updates (a failed update could break its own permissions).

2. **`agenticml-hosted`** (`deploy/aws/cloudformation/hosted.yaml`), created
   and updated only by the deploy workflow through the CloudFormation
   role. It is the Terraform stack, translated, with these changes:

   - **Parameters:** `ImageTag` (required, the commit SHA),
     `HostedZoneId` (the existing public `agenticml.xyz` zone),
     `Hostname` (default `app.agenticml.xyz`), `AlarmEmail`,
     `DesiredCount` (default 2, min 0), `MultiAZ` (default `false`),
     `FirebaseProject` (default empty), `FirebaseApiKey` (default empty),
     `OpenSignup` (default `false`, allowed `true`/`false`),
     `VpcCidr` (default `10.42.0.0/16`). No bucket-name or final-snapshot
     parameters: let CloudFormation name the buckets, and use
     `DeletionPolicy: Snapshot` on RDS.
   - The image is `<bootstrap ECR URI>:<ImageTag>`. Import the repository
     URI with `Fn::ImportValue` from the bootstrap stack's exported
     output (export name `agenticml-hosted-bootstrap-EcrRepositoryUri`),
     or pass it as a parameter; pick one and say which.
   - **Network (no NAT):** VPC with IPv6, internet gateway, and three
     pairs of subnets in the first two AZs (`Fn::GetAZs`):
     - ALB subnets `10.42.0.0/24`, `10.42.1.0/24` (public, IPv6 as now);
     - task subnets `10.42.20.0/24`, `10.42.21.0/24` (public route to the
       internet gateway, `MapPublicIpOnLaunch` not needed; the service
       sets `AssignPublicIp: ENABLED`);
     - data subnets `10.42.10.0/24`, `10.42.11.0/24` (private, no route
       to the internet) for RDS and EFS mount targets.
     Separate ALB and task subnets keep `AGENTICML_SERVER_TRUSTED_PROXY`
     equal to the ALB subnet CIDRs only. Keep the S3 gateway endpoint,
     attached to the task subnets' route table. No NAT gateway, no
     Elastic IP.
   - **Security groups** as in Terraform: ALB 80/443 from anywhere (IPv4
     and IPv6); task 8080 from the ALB SG only, egress all; RDS 5432
     from the task SG; EFS 2049 from the task SG.
   - **TLS:** `AWS::CertificateManager::Certificate` for `Hostname` with
     DNS validation and `DomainValidationOptions` → `HostedZoneId`
     (CloudFormation creates the validation record itself). HTTPS
     listener with `ELBSecurityPolicy-TLS13-1-2-2021-06`; port 80
     redirects to 443. Route 53 `A` and `AAAA` alias records for
     `Hostname` to the ALB.
   - **ALB:** dualstack, idle timeout 300, `drop_invalid_header_fields`,
     access logs to the logs bucket under `alb/`. Target group: IP
     targets on 8080, health check `/healthz`, deregistration delay 120.
     The logs bucket policy must let ELB in `us-east-2` write
     (ELB account `033677994240` for this region; check the current AWS
     docs and note the source in a comment).
   - **ECS:** cluster with Container Insights, log group
     `/ecs/agenticml-hosted` (30 days), task definition (512 CPU / 1024
     MB, X86_64, EFS volume with transit encryption and access point IAM,
     `stopTimeout` 120, `PGPASSWORD` from the RDS-managed secret's
     `password` key via `MasterUserSecret.SecretArn`), service (Fargate
     platform 1.4.0, ECS Exec on, 100/200 deployment percents, circuit
     breaker with rollback, grace period 60, `AssignPublicIp: ENABLED`
     in the task subnets). Environment as in Terraform's
     `locals.environment`, except the Firebase variables are left out
     entirely (`Fn::If` + `AWS::NoValue`) when `FirebaseProject` is
     empty. `OpenSignup = true` with an empty `FirebaseProject` must fail
     the deploy before anything changes: use a `Rules` assertion.
   - **RDS:** as Terraform (Postgres 16, `db.t4g.small`, gp3 20→100 GB,
     encrypted, `rds.force_ssl=1` parameter group, managed master
     password, 7-day backups, deletion protection, `MultiAZ` parameter,
     data subnets). `DeletionPolicy: Snapshot`,
     `UpdateReplacePolicy: Snapshot`.
   - **EFS:** encrypted, generalPurpose/elastic, mount targets in the data
     subnets, access point uid/gid 10001 at `/agenticml` mode 0700, and
     the same three-statement file system policy. `DeletionPolicy` and
     `UpdateReplacePolicy: Retain`.
   - **S3:** objects bucket (versioned, SSE-S3, public access blocked,
     owner-enforced, TLS-only policy, noncurrent versions expire after
     30 days, abort multipart after 7) and logs bucket (90-day
     expiration). Both `Retain`.
   - **IAM:** execution and task roles named `agenticml-hosted-execution`
     and `agenticml-hosted-task`, with the same policies as `iam.tf`
     (including the HeadBucket/ListBucket comment). Same ECS trust
     conditions.
   - **Backup:** vault, daily plan (05:00 UTC, 35 days), backup role
     with the two AWS managed policies, selection of the EFS file system
     and the RDS instance. Vault `Retain`.
   - **Monitoring:** SNS topic with an email subscription to
     `AlarmEmail`, and the same six alarms with the same thresholds,
     periods and missing-data handling as `monitoring.tf`.
   - **Outputs:** `ServiceUrl`, `AlbDnsName`, `ClusterName`,
     `ServiceName`, `LogGroup`, `ObjectsBucket`, `LogsBucket`, `EfsId`,
     `DbInstanceId`, `TaskSecurityGroup`, `TaskSubnets` (for the
     runbook's ECS Exec, restore drill and benchmark commands).
   - Tag every resource that supports tags with `Project=agenticml-hosted`
     (stack-level tags from the workflow are enough).

## Deploy workflow (`.github/workflows/deploy.yml`)

- `workflow_dispatch` with optional input `ref` (as now); `environment:
  hosted`; concurrency group `hosted-deploy`, no cancel; `permissions:
  contents: read, id-token: write`; same pinned action majors as now.
- Steps: checkout `ref` (no persisted credentials); assume
  `vars.AWS_DEPLOY_ROLE_ARN`; ECR login; build-or-reuse the immutable
  `<sha>` image (keep the existing logic that tells a missing tag from
  other errors, and use the repository from the bootstrap stack);
  then:

  ```sh
  aws cloudformation deploy \
    --stack-name agenticml-hosted \
    --template-file deploy/aws/cloudformation/hosted.yaml \
    --role-arn "$CFN_ROLE_ARN" \
    --capabilities CAPABILITY_NAMED_IAM \
    --no-fail-on-empty-changeset \
    --tags Project=agenticml-hosted \
    --parameter-overrides ImageTag="$sha" HostedZoneId=... AlarmEmail=... \
      DesiredCount=... MultiAZ=... FirebaseProject=... FirebaseApiKey=... OpenSignup=...
  ```

  Every parameter comes from `hosted` environment variables:
  `HOSTED_ZONE_ID`, `HOSTED_ALARM_EMAIL`, `HOSTED_DESIRED_COUNT`
  (default 2), `HOSTED_MULTI_AZ` (default false),
  `HOSTED_FIREBASE_PROJECT`, `HOSTED_FIREBASE_API_KEY`,
  `HOSTED_OPEN_SIGNUP` (default false), plus `AWS_CFN_ROLE_ARN` and
  `AWS_REGION` (default `us-east-2`). Pass them through `env:` and quote
  them; never interpolate `${{ }}` into the script body. Empty Firebase
  values must reach the template as empty strings.
- On failure print the last 30 stack events (`describe-stack-events`)
  so the cause shows in the log. After success, check
  `services-stable`-equivalent state through `describe-services`
  (CloudFormation already waits for the ECS deployment; the circuit
  breaker turns a bad image into a failed, rolled-back stack update).
- A configuration change (for example turning sign-up off) is: change
  the environment variable, re-run the workflow with the currently
  deployed SHA. The image is reused; only the task definition changes.

## Tests and checks

- `tests/test_deploy_cloudformation.py` loads both templates with a
  PyYAML loader that accepts CloudFormation short tags (`!Ref`,
  `!GetAtt`, `!Sub`, `!If`, `!Equals`, `!Not`, `!Select`, `!GetAZs`,
  `!ImportValue`, `!Join`, `!Split`, `!Cidr`, `!Condition`, ...) and
  asserts the invariants a later edit must not lose:
  - no `AWS::EC2::NatGateway` or `AWS::EC2::EIP` in `hosted.yaml`;
  - RDS: `DeletionPolicy`/`UpdateReplacePolicy` `Snapshot`,
    `DeletionProtection` true, `StorageEncrypted` true,
    `PubliclyAccessible` false, `ManageMasterUserPassword` true;
  - EFS file system, both buckets, backup vault: `Retain`;
  - task security group ingress only from the ALB security group, on
    8080; RDS and EFS ingress only from the task security group;
  - service uses `AssignPublicIp: ENABLED` and the task subnets; RDS
    subnet group and EFS mount targets use the data subnets;
  - `AGENTICML_SERVER_TRUSTED_PROXY` is built from the ALB subnet CIDRs
    only;
  - the Firebase environment entries are conditional and a `Rules`
    assertion ties `OpenSignup=true` to a non-empty `FirebaseProject`;
  - bootstrap: deploy role trust has exactly the `sub`
    `repo:agenticML/agenticml-lite:environment:hosted` and `aud`
    `sts.amazonaws.com`; the deploy role's `iam:PassRole` is limited to
    the CloudFormation role with `PassedToService`
    `cloudformation.amazonaws.com`; ECR repository is immutable;
  - the workflow file references `hosted.yaml`, `--role-arn`, and no
    `terraform`.
  PyYAML is already in the testbed venv; if a fresh CI venv lacks it,
  add it to the test dependencies (report it).
- `cfn-lint` passes on both templates locally (install it into a
  scratch venv, not the testbed venv) and in the `deploy-check` job.
- `testbed/.venv/bin/python -m pytest -q tests` passes.
- No AWS calls of any kind (no `aws cloudformation validate-template`
  against a real account). The owner runs the first deploy.

## Constraints and conventions

- YAML templates, 2-space indent, short-form intrinsics, one resource
  per logical block with a short comment only where the reason is not
  obvious (match the comment density of the Terraform files).
- Logical and physical names keep the `agenticml-hosted` prefix so the
  runbook commands (`--cluster agenticml-hosted --service
  agenticml-hosted`, log group `/ecs/agenticml-hosted`) still work.
- Region is not hard-coded in resources; use `AWS::Region`,
  `AWS::AccountId`, `AWS::Partition`. The ELB log-delivery account
  mapping may list only `us-east-2` and must fail clearly elsewhere.
- No secrets in templates, parameters or workflow variables: the
  Firebase web API key is public by design; the database password stays
  in the RDS-managed secret.
- Do not change server code, the Dockerfile, the entrypoint or the
  smoke test. If the template needs a server change, stop and report it.

## Edge cases

- **First run:** the stack does not exist yet; `aws cloudformation
  deploy` creates it. The image is pushed before the stack is created,
  so tasks start on a real image; no `desired_count=0` step.
- **Failed first create** rolls back and deletes the stack, except the
  `Retain` resources (buckets, EFS, backup vault) which stay behind; the
  runbook must say how to find and delete those before retrying (the
  docs agent writes it; the coder lists the resources).
- **RDS in rollback:** a failed create with RDS already up leaves a
  final snapshot because of `DeletionPolicy: Snapshot`; note it.
- **Rollback of a bad image:** the circuit breaker fails the ECS
  deployment, CloudFormation rolls the stack back to the previous task
  definition; the workflow fails with stack events printed.
- **Stack stuck in `UPDATE_ROLLBACK_FAILED`:** runbook item, not code.
- **Rotating the managed DB secret** still needs a new task deployment
  (re-run the workflow with the same SHA after forcing a new task
  definition, or `aws ecs update-service --force-new-deployment`).
- **OIDC provider already exists:** bootstrap parameter set → no
  provider resource, the role trusts the given ARN.
