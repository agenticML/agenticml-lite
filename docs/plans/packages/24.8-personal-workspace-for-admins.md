# Package 24.8: Personal workspace for every verified sign-in

Nov 13, 2026 · Supervisor plan · Release 3.0 · Coder: Sonnet · Size: S

## Goal

With open sign-up on, a stranger's first verified sign-in gets a free
personal workspace, but an account created by the admin-email list
(package 24.7) gets none: the owner signs in as server admin and lands on an
empty `/workspaces`. Owner's request (Nov 13, 2026): admins get a workspace
too.

Rule after this package: **with open sign-up on, a verified Firebase sign-in
whose account has no workspace membership gets the free personal workspace**
(same slug and name rules as sign-up; the free-workspace limit still
applies). With open sign-up off, nothing changes.

## Facts from the code (`src/agenticml/server/webauth.py`, `_firebase_auth`)

- The sign-up write transaction (about lines 1191-1209) runs for every
  sign-in that is not an invite redemption:
  - `account is None and listed` → `_firebase_admin_create` (no workspace);
  - `elif account is None and self.open_signup` → `_firebase_open_signup`
    (account + `_create_signup_workspace`);
  - `elif account is not None and self.open_signup` →
    `_recover_signup_workspace`, which today only acts when
    `created_by == "signup"`, the email is verified, the account has no
    memberships, **and** the `signup_pending:<id>` marker exists (set only
    after a failed store preparation).
- `_create_signup_workspace` checks `plans.free_workspaces_per_account`
  against `owned_free_count`, allocates the slug from the email local part
  and creates a `personal=1` free workspace.
- `_prepare_created_workspace` prepares the store, rolls the workspace back
  and sets the pending marker on failure, and deletes the marker on success.
  The `workspace.create` audit (`via="signup"`) follows it.

## Changes (Sonnet)

1. **New list admins**: in the list branch, after `_firebase_admin_create`
   returns an account and `self.open_signup` is on, set
   `created_workspace = self._create_signup_workspace(account, claims, tx,
   plans)` in the same transaction.
2. **Existing accounts without a workspace**: change
   `_recover_signup_workspace` (rename it if clearer, e.g.
   `_personal_workspace_if_none`) so that, with open sign-up on, it creates
   the personal workspace when the sign-in is verified
   (`email_verified_for_link`) and the account has **no membership rows at
   all**. Drop the `created_by == "signup"` and pending-marker conditions:
   the no-membership check already covers the failed-store case. Keep the
   marker handling in `_prepare_created_workspace` as is (harmless).
3. **Invite redemptions** keep today's behaviour (they always end with a
   membership).
4. Audit: unchanged (`workspace.create`, `via="signup"`, actor = the
   account login). No new audit action.

## Review change (Nov 13, 2026)

The supervisor review kept the moderation rule that an admin-deleted sign-up
workspace is not recreated at the next sign-in:

- Sign-up accounts (`created_by == "signup"`) keep the old rule: a workspace
  is recreated only after a failed store preparation (pending marker).
- Other accounts (list admins, CLI- or `/admin`-created) get the personal
  workspace at most once, tracked by a `personal_workspace:<account_id>`
  setting written in the same transaction; a failed store preparation clears
  it so the next sign-in retries.

## Edge cases

- Open sign-up off: no change for anyone (list admins still get no
  workspace; `/admin` "New workspace" is the way).
- Unverified email or untrusted provider: no workspace.
- An account with any membership (even in a suspended workspace) gets
  nothing.
- `free_workspaces_per_account` reached (or 0): no workspace, as today.
- Slug taken: `allocate_slug` picks the next free one, as for sign-up.
- Concurrent sign-ins of the same account: both run under
  `advisory_lock('users')`; the second sees the first's membership.
- Store preparation fails: the workspace is rolled back (as today) and the
  next sign-in tries again (no membership).

## Tests

In `tests/test_server_admin_emails.py` and `tests/test_server_signup.py`
(both run on SQLite and Postgres):

- Open sign-up on + listed email, first sign-in: server admin **and** a
  personal free workspace; `/workspaces` lists it; audits `account.create`
  and `workspace.create`.
- Open sign-up off + listed email: server admin, no workspace (unchanged).
- Existing list-created admin with no workspace, open sign-up on: the next
  sign-in creates the workspace; a later sign-in does not create a second.
- A sign-up account whose only membership was removed: the next sign-in
  gets a personal workspace again (new behaviour; replaces any test that
  asserted the old marker-only recovery, which must be updated, not
  deleted, and the change reported).
- Account with a membership: nothing created.
- `free_workspaces_per_account=0`: nothing created.
- Unverified sign-in of an existing account without workspaces: nothing.
