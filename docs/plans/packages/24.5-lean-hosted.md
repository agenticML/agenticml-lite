# Package 24.5 †: Lean hosted setup (~$60/month) and deploys from `dev`

Nov 12, 2026 · Supervisor plan · Release 3.0 · AWS roadmap Phase 3

## Goal

Before the first deploy (AWS roadmap Phase 3), cut the hosted stack from
about $100–110/month to about **$60–65/month**, and let the deploy workflow
run from `dev` without first copying it to `main`. Owner decisions
(Nov 12, 2026): "switch to a leaner AWS setup that costs around 60 dollars a
month", "make the deployment to dev branch instead of main", supervisor picks
the details.

## Choices

Keep the architecture (ALB with the issued ACM certificate, ECS Fargate,
RDS Postgres, EFS, S3, Backup, alarms); shrink its sizes. A single EC2 host
with Caddy and SQLite would cost ~$20 but throws away the CloudFormation
work, the ACM certificate, Postgres and rolling deploys; the owner asked for
~$60, which the current design reaches with these changes:

| Change | Saving/month |
| --- | --- |
| One Fargate task by default instead of two (rolling deploys still start the new task before stopping the old one, so no downtime) | ~$18 + $3.65 IPv4 |
| ARM64 (Graviton) tasks instead of x86 | ~$3.60 |
| RDS `db.t4g.micro` instead of `db.t4g.small` | ~$12 |
| Container Insights off; the running-tasks alarm uses the free ALB `HealthyHostCount` metric instead | ~$3–5 |

Estimate after the change (us-east-2, on demand): Fargate 0.5 vCPU / 1 GB
ARM ~$14.40, ALB ~$17–18, public IPv4 (ALB ×2, task ×1) ~$11, RDS micro with
20 GB gp3 ~$14, EFS ~$1–2, S3/ECR ~$1–2, CloudWatch logs and 6 alarms ~$1–2,
Backup ~$1, Secrets Manager $0.40, cost alerts ~$0.60: **about $62–66**.

Unchanged on purpose: single-AZ RDS (already), no NAT, task size 0.5 vCPU /
1 GB, backups (pennies at this size), the bootstrap stack's $100 budget (the
owner may lower it to $75 by redeploying bootstrap; not required).

Deploys from `dev`: add a `push` trigger on `dev` (limited to paths that
change the image or the stack). Push-triggered workflows run from the pushed
commit's file, so nothing has to land on `main` first. Every run still waits
for the `hosted` environment's required reviewer, so a merge to `dev`
queues a deploy that the owner approves; concurrency keeps at most one
waiting run. `workflow_dispatch` stays for manual runs once the file reaches
`main`.

## Files to touch

- `deploy/aws/cloudformation/hosted.yaml`: `DesiredCount` default 1;
  `RuntimePlatform.CpuArchitecture: ARM64`; `DBInstanceClass: db.t4g.micro`;
  cluster `containerInsights: disabled`; replace `RunningTasksAlarm`
  (`ECS/ContainerInsights` `RunningTaskCount`) with `HealthyHostsAlarm`
  (`AWS/ApplicationELB` `HealthyHostCount` per target group, `Minimum` < 1
  for 5 × 60 s, missing data breaching, only while `DesiredCount` > 0,
  `DependsOn: Service` so a create or scale-up from zero does not alarm),
  named `agenticml-hosted-healthy_hosts`.
- `deploy/aws/cloudformation/bootstrap.yaml`: add
  `elasticfilesystem.amazonaws.com` to the CloudFormation role's
  `ServiceLinkedRoles` list (backlog item; takes effect only when the owner
  next redeploys bootstrap, so the one-off CLI step 3.0b stays for now).
- `.github/workflows/deploy.yml`: `push` on `dev` with a `paths` filter
  (`src/**`, `pyproject.toml`, `deploy/aws/**` except Markdown and
  `bootstrap.yaml`, `.github/workflows/deploy.yml`);
  `workflow_dispatch` gains a `desired_count` choice input (`1`, `0`, `2`;
  default `1`) that replaces the `HOSTED_DESIRED_COUNT` variable (which is
  set to 2 today and would undo the saving). Push runs leave `DesiredCount`
  out of the overrides, so an existing stack keeps its count and a new one
  gets the default 1; the final check compares the service's running and
  desired counts; build the image for
  `linux/arm64` through QEMU on the x86 runner
  (`docker/setup-qemu-action`) and tag it `<sha>-arm64`, so an x86 image of
  the same commit is never reused.
- `tests/test_deploy_cloudformation.py`: update the sizing, architecture,
  alarm and workflow assertions; add tests for the push trigger, the arm64
  build, the desired-count input and the EFS service-linked role.
- Docs: `deploy/aws/README.md` and `docs/HOSTED.md` (variables, first
  deploy, alarms, cost), `docs/plans/aws-deployment-roadmap.md` (decisions,
  cost, Phase 3 steps), `docs/plans/on-prem-roadmap.md` (package row,
  backlog entry).

## Constraints and conventions

- Agents never call AWS; the owner runs bootstrap, approves deploys and runs
  3.0b.
- `run:` blocks take values from `env:` only (existing test).
- Template under the 51,200-byte inline limit; `cfn-lint` clean.
- Security-sensitive (IAM in bootstrap, deploy trigger): Sonnet review plus a
  second read-only review from Cursor.

## Edge cases

- Push runs have no `inputs`: `DesiredCount` is not passed (the stack keeps
  its value), `ref` falls back to the pushed SHA; the "commit is on the dispatching ref" guard only runs when
  `ref` is given.
- An older x86 `<sha>` tag in ECR (none exists; no deploy has run) cannot be
  picked up, because the new tag carries `-arm64`.
- Scaling to 0 removes the healthy-hosts alarm (as before with running
  tasks).
- `db.t4g.micro` has 1 GB RAM (~80–100 connections); one or two server
  processes are far below that.
- All pinned hosted dependencies have `manylinux` aarch64 wheels
  (psycopg-binary, cryptography, cffi, charset-normalizer), so the arm64
  build compiles nothing.

## First deploy fix: immutable OIDC subjects

The first deploy run (Nov 12, 2026) failed at the AWS credentials step with
`Not authorized to perform sts:AssumeRoleWithWebIdentity`. The repository
uses GitHub's immutable OIDC subjects (`use_immutable_subject: true`), so the
token's subject is
`repo:agenticML@279794012/agenticml-lite@1435335342:environment:hosted`, while
the deploy role trusted only `repo:agenticML/agenticml-lite:environment:hosted`.

Fix, in `bootstrap.yaml`: a `GitHubSubjectPrefix` parameter, default this
repository's immutable prefix, with `AllowedPattern` limited to
`repo:OWNER@ID/REPO@ID` or empty. The trust condition is still one exact
`StringEquals` value: `${GitHubSubjectPrefix}:environment:hosted`, or
`repo:${GitHubRepo}:environment:hosted` when the prefix is empty. Turning
immutable subjects off on GitHub would also work, but it is the weaker
setting (a renamed or recreated repository could reuse the name). The owner
redeploys the bootstrap stack, which also applies the EFS service-linked-role
change. Tests check the parameter, its pattern and the trust condition.

The re-run then built the arm64 image and pushed its layers, but `docker
push` failed with 403 Forbidden on a `HEAD` request for a manifest by
digest. The deploy role's `EcrPush` statement lacked `ecr:BatchGetImage`,
which ECR requires for manifest reads. It now has it, still scoped to the one
repository; a test pins the role's full ECR action list.
