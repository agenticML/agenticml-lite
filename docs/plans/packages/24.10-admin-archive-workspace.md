# Package 24.10 †: Archive a workspace on `/admin`

Nov 13, 2026 · Supervisor plan (numbered 24.10 because PR #61 took 24.9 for email logins on the Keys and Team pages) · Release 3.0 · Coder: Sonnet · Size: S–M

† Security-sensitive: it changes who can reach a workspace and how the free
workspace limit is counted. The supervisor does the second review.

## Goal

Server admins can suspend and resume workspaces on `/admin`, but a workspace
the owner no longer wants (for example a suspended test workspace) still
counts as theirs: it blocks the free personal workspace (packages 18c and
24.8) and clutters the list. The owner first asked for Delete (Nov 13, 2026),
then chose **Archive** instead: reversible, data kept, only on `/admin`.
Permanent deletion stays a server CLI command (`agenticml server workspaces
delete`). Rules for workspace owners and members come later.

A first version of this package added a web Delete; it was replaced before
merging. Remove its route, handler, UI and tests from the working tree.

## Behaviour

- **Archive** (`/admin`, server admins only): the workspace is suspended and
  marked archived in one transaction. Nobody can open it or sync to it (as
  with a suspended workspace: 404 everywhere, keys rejected). Not allowed for
  `default`.
- An archived workspace:
  - is listed in a separate "Archived" table on `/admin`, not in the main
    Workspaces table;
  - does not count toward its owner's free workspace limit
    (`owned_free_count`);
  - does not count as a membership for package 24.8's "account without any
    workspace" rule, so the owner's next verified sign-in can get the free
    personal workspace (subject to 24.8's once-only marker for non-sign-up
    accounts and the sign-up rule for sign-up accounts);
  - keeps its runs, files, objects, keys and memberships.
- **Restore**: clears the archived mark and leaves the workspace
  **suspended**; the admin then clicks Resume to reopen it. Restoring is
  refused with 409 when it would take the owner over the free workspace
  limit (the owner already has their free workspace again): the admin can
  change the plan to `custom` first or archive the other one.

## Changes (Sonnet)

1. **Migration 0009**: `ALTER TABLE workspaces ADD COLUMN archived_at TEXT;`
   (NULL = not archived). The status CHECK constraint is not touched.
2. **Repo** (`db/workspaces.py`):
   - `WorkspaceRepo.archive(slug)` and `WorkspaceRepo.restore(slug)`, each
     in one write transaction under `advisory_lock('users')` with
     `tx.cross_workspace(...)`, as `update` does. Archive: refuse `default`
     and an already archived workspace (`ClientError`); set
     `status='suspended'`, `archived_at=<now>`. Restore: refuse a workspace
     that is not archived; check the owner's free limit (needs `plans`,
     passed in by the route; skip the check without a limits file or for a
     `custom` plan); clear `archived_at`. Return the row.
   - `owned_free_count` ignores archived workspaces
     (`AND w.archived_at IS NULL`).
   - `list()` (used by `/admin`) returns `archived_at`.
3. **Sign-in** (`webauth.py` `_personal_workspace_if_none`): the
   "no membership rows" check ignores memberships in archived workspaces.
   Nothing else in 24.8 changes.
4. **API** (scope `server_admin`, handled in `_admin_workspaces`, route
   names added to the isolation case table and the route-table test):
   `POST /api/admin/workspaces/<slug>/archive` and
   `POST /api/admin/workspaces/<slug>/restore`, both with an empty JSON
   body `{}` through `read_json` (CSRF and JSON checks). 200 with the
   workspace (`_admin_public` plus `archived_at`); 404 unknown; 400
   `default`; 409 already archived / not archived / restore over the free
   limit. Audit `workspace.archive` and `workspace.restore` (target id,

   refuse `status: "active"` (Resume) for an archived workspace with 409

   same `data-label` cells; columns Slug, Name, Plan, Storage, Archived,

## Edge cases

- `default`: never archived (400); the UI offers no Archive for it.
- Archiving an archived workspace or restoring an active one: 409.
- Resume (PATCH status active) on an archived workspace: 409.
- Sync key of an archived workspace: rejected like a suspended one.
- Concurrency: archive, restore, resume and sign-in counting all run under
  `advisory_lock('users')`.
- Non-admins and anonymous: unknown-route answers; CSRF refused.

## Tests

- Repo and API (new `tests/test_server_admin_archive.py`, SQLite and
  Postgres): archive (status suspended, `archived_at` set, audit), restore
  (cleared, still suspended, audit), `default` 400, double archive 409,
  restore of a non-archived 409, resume of archived 409, unknown 404,
  non-admin/anonymous unknown-route answers, CSRF refused, sync key
  rejected while archived; restore over the free limit 409 (limits file
  with 1 free workspace, owner given a new personal workspace meanwhile).
- Free limit and 24.8: an owner whose only free workspace is archived is
  under the limit again; a list admin whose only workspace (created on
  `/admin`) is archived gets a personal workspace at the next sign-in with
  open sign-up on; a sign-up account whose workspace is archived does not
  (sign-up rule).
- Migration: a database at version 8 upgrades; existing workspaces have
  `archived_at` NULL.
- UI (`testbed/tests/test_server_admin_dashboard.py`): Archive absent for
  `default`; archiving moves the row to the Archived table; Restore moves
  it back as suspended; Archived section hidden when empty; no overflow at
  375px with the dialog open.
