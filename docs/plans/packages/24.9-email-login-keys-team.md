# Package 24.9: Email logins on the Keys and Team pages

Nov 13, 2026 · Supervisor plan · Release 3.0 · Coder: Sonnet · Size: S · †

## Goal

In hosted (Firebase) mode every account's login is an email address. Two
dashboard features reject emails with 400, so they are broken on
`app.agenticml.xyz`:

1. **Keys page.** `POST /api/w/<slug>/keys` with an email user (the default
   is `principal.user`) answers 400 "invalid or reserved key name": an email
   login cannot create an API key.
2. **Team page.** `PATCH` and `DELETE /api/w/<slug>/members/<email>` and
   `POST /api/w/<slug>/members/<email>/invite` answer 400 "invalid or
   reserved user name": changing a member's role, removing a member and
   "Invite link" all fail for email accounts.

Found by a design-board capture agent running dev (c93a0b3) locally in
hosted mode; it had to stub these responses.

After this package, wherever the key and team handlers take a **login**
(a user name), they accept what the database layer accepts: an email
(lowercased) or a key-style name. **Key names** keep the strict
`[A-Za-z0-9._-]{1,64}` rule.

## Facts from the code

- `src/agenticml/server/keys.py`: `_NAME = [A-Za-z0-9._-]{1,64}`;
  `validate_name()` also rejects `env`, `.`, `..` and raises
  `ClientError("invalid or reserved key name")`.
- `src/agenticml/server/db/workspaces.py`: `validate_login(login)` returns
  the lowercased email when `is_email_login(login)` (`[^\s@]+@[^\s@]+\.[^\s@]+`,
  at most 254 chars), otherwise calls `validate_name(login)` and returns it.
  The database layer already uses it: `UserRepo._new` (`db/repos.py:118`),
  account lookups, workspace invites. `KeyRepo.create` looks the user up with
  `self.users.get(user)`, so it already works for emails.
- `src/agenticml/server/keyspage.py` `handle()`:
  - GET `?user=` filter: `validate_name(user)` (rejects emails).
  - POST: `validate_name(name)` for the key name (correct), then
    `validate_name(user)` for the key's user (bug 1).
  - DELETE `/keys/<name>`: `_NAME.fullmatch(name)` on the key name (correct).
- `src/agenticml/server/userspage.py` `handle()`:
  - POST `/users` (members create): `_user_name(name)` → `validate_name`.
    Out of scope (see Edge cases).
  - `/users/<name>/invite` and `/users/<name>` (PATCH, DELETE):
    `_NAME.fullmatch(name) or name in (".", "..")` (bug 2).
  - The final `except ValueError` maps "invalid or reserved key name" to
    "invalid or reserved user name".
- `src/agenticml/server/routes.py` maps `/api/w/<slug>/keys...` to
  `keyspage.handle` and `/api/w/<slug>/members/<login>[/invite]` to
  `userspage.handle` with `/api/server/users/<login>[/invite]`. The path is
  URL-decoded before routing (`webauth.py`, `unquote(..., errors="strict")`),
  and the dashboard sends `encodeURIComponent(user.name)`, so `%40` arrives
  as `@`.

## Changes (Sonnet)

1. **`keyspage.py`**
   - Import `validate_login` from `.db.workspaces`.
   - GET `?user=` filter: `user = validate_login(user)` instead of
     `validate_name(user)`.
   - POST: keep `validate_name(name)` for the key name and the existing
     order (`can_create` before validating the user). Replace
     `validate_name(user)` with `user = validate_login(user)` (still skipped
     for the `env_default` case). Pass the normalized `user` to
     `keys.create`.
   - A non-email, non-string or malformed user must still answer 400.
     `validate_login` raises "invalid or reserved key name" for a bad user,
     which is misleading on the user field: raise
     `ClientError("invalid or reserved user name")` instead (catch and
     re-raise, like `userspage._user_name`).
   - DELETE `/keys/<name>`: unchanged (key name).
2. **`userspage.py`**
   - Add a helper, e.g. `_login(name)`: returns `validate_login(name)` and
     turns its `ClientError` into `ClientError("invalid or reserved user
     name")`.
   - Replace both `_NAME.fullmatch(name) or name in (".", "..")` checks (the
     `/invite` branch and the `PATCH`/`DELETE` branch) with
     `name = _login(name)`, so later lookups, `name == principal.user`
     comparisons, audit targets and responses use the normalized login.
   - Leave POST `/users` (`_user_name`) unchanged.
   - Drop the `_NAME` import if it becomes unused (keep it in `keyspage.py`,
     which still checks key names).
3. Do not change `keys.py` `_NAME`, `validate_name`, or the key file parser.

## Constraints and conventions

- Follow the surrounding style (double quotes in these two files, existing
  error strings and status codes).
- Do not loosen key-name validation: `@` in a key name stays 400.
- No dashboard JS change is expected; report it if one turns out to be
  needed.
- No change to authorization: role checks (`allowed`, `can_create`) and the
  owner and last-admin rules stay as they are.

## Edge cases

- Mixed-case email in the URL or payload (`Bob@Example.com`): normalized to
  lowercase, so it finds the stored login. Self checks (`you cannot remove
  yourself`, self re-invite) must compare the normalized value.
- `env`, `.`, `..`, empty, over-long (more than 254 chars), `a@b` (no dot in
  the domain), and non-string users stay 400 with "invalid or reserved user
  name".
- Unknown but well-formed email: 404 "not found" (PATCH, DELETE, invite) or
  404 "unknown user" (key create), as for key-style names today.
- Invite link for an email member who belongs to another workspace:
  `UserRepo.create_invite` refuses it with 403
  `CROSS_WORKSPACE_CREDENTIALS` by design. With open sign-up on, everyone
  who signed up on their own owns a personal workspace, so this will be
  common in hosted mode. Not changed here; recorded in the Backlog (see below).
- POST `/members` (add a member by name) still rejects emails; the hosted
  Team page adds people through `/invites`, which already takes emails.
  Not changed here.

## Tests and checks

Failing tests first, then the fix.

- **`tests/test_server_firebase.py`** (hosted mode: `firebase_running`,
  `_member_account`, `_post_firebase`, `_live_token`): an email admin signed
  in with Firebase (session cookie + CSRF) in the default workspace:
  - creates a key for themself through `POST /api/w/default/keys`
    (no `user` in the payload, and with `user` set to their email) → 201,
    record user is the email; `GET /api/w/default/keys?user=<email>` lists it;
  - changes an email member's role through `PATCH
    /api/w/default/members/<email>` (URL-encoded `%40`) → 200;
  - creates an invite link through `POST
    /api/w/default/members/<email>/invite` for a member who belongs to no
    other workspace → 200 with `invite_url`;
  - removes that member through `DELETE /api/w/default/members/<email>`
    → 200;
  - mixed-case email in the URL finds the member;
  - a key name containing `@` is still 400; a user value `a@b`, `env` or
    `..` is 400 "invalid or reserved user name".
  Put the shared setup in a fixture or helper; keep each test focused.
- **`testbed/tests/test_server_firebase_dashboard.py`** (it already has the
  fake Firebase SDK and a hosted server): one `ui` test where the signed-in
  email admin creates a key on the Keys page and changes a member's role on
  the Team page, with no error shown.
- Existing tests that asserted the old behaviour for logins (if any) are
  updated only when the old assertion was the bug; report each one.
- Run from the repo root: `testbed/.venv/bin/python -m pytest -q tests`.
- Run from `testbed/`: `.venv/bin/python -m pytest -q -m ui`.
