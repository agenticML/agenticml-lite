# Package 24.7 †: Self-serve server admins

Nov 13, 2026 · Supervisor plan · Release 3.0 · Coder: Sonnet (24.7a–c),
prose Antigravity (24.7d) · Size: M

† Security-sensitive: this grants server admin from deploy config and from
the web. Codex and Cursor are disabled, so the supervisor does the second
read-only review (owner's rule) and records it in the PR.

## Goal

Running the hosted service must not need ECS Exec. With Firebase on,
`/setup` is closed, and today server admin can only be granted with
`agenticml server accounts ... --server-admin` over ECS Exec. After this
package:

1. The owner puts their email in the deploy config (`HOSTED_ADMIN_EMAILS`),
   deploys, signs in with Google and is a server admin.
2. Server admins add and remove other server admins on `/admin`.
3. Server admins create a customer workspace on `/admin` for an owner email
   that has no account yet; the owner's first verified sign-in links it.

ECS Exec and the server CLI stay as the break-glass path.

Owner decisions (Nov 13, 2026):

- First list entry: the owner's Google email (set as a GitHub variable, not
  committed).
- Removing an email from the list revokes server admin **at that person's
  next sign-in**, but only rights the list granted. Rights granted on
  `/admin` or with the CLI are kept.

## Facts from the code (Nov 13, 2026)

- `accounts.server_admin` is 0/1 with no record of who granted it
  (migrations 0003, 0004; latest migration is 0007).
- `AccountRepo.set_server_admin(login, enabled)` (`db/workspaces.py:193`)
  opens its own write transaction, has no last-admin guard and is used by
  the CLI only. No last-server-admin guard exists anywhere.
- `server_admin` is read from the database on every request
  (`webauth.py` `_principal_from_session`, `users.resolve`), so a change
  takes effect on the next request; no session needs to be ended.
- A credential-less account (no password, identity or `firebase_uid`, and
  `created_by != 'legacy run owner'`) is `claimable`: the first verified
  Firebase sign-in with that email links it (`_firebase_find_or_claim`,
  `webauth.py:1255`). `email_verified_for_link(claims)` (`firebase.py:350`)
  is the "verified sign-in" test (Google or Firebase email/password, email
  verified).
- `_firebase_auth` (`webauth.py:1068-1252`) resolves the account on three
  paths: invite redemption (`InviteRepo.redeem_firebase`), lookup by uid or
  claim inside the write transaction at about line 1180, and open sign-up.
  A second write transaction at about line 1221 refreshes the email and
  re-reads the account row before the session is created.
- A server admin with no membership lands on `/workspaces` ("You are not a
  member of any workspace") with an Admin button, and `/admin` works.
- `WorkspaceRepo.create` requires an existing owner account
  ("workspace needs an existing owner account").
- Settings reach the server only through `cli.py` (`_open_signup_from_args`
  pattern, `AGENTICML_SERVER_*` env vars); `serve` → `make_server` →
  `IngestServer.__init__` → `WebAuth.__init__` take plain kwargs. `server up`
  writes systemd and launchd units with the same flags (`up.py`).
- The hosted container passes settings as environment variables, so no
  entrypoint or Dockerfile change is needed.
- `tests/test_deploy_cloudformation.py` checks the exact parameter set,
  forbids `${{` in `run:` blocks and forbids email addresses in
  `deploy.yml` and the templates.
- Team page UI copy assumes passwords: "They choose their own password."
  (`app.js` about line 4651) and "This signs them out and clears their
  password." (about line 5057), which is wrong with Firebase on.

## 24.7a † Admin emails and the server-admin guard (Sonnet)

Files: `src/agenticml/server/db/migrations/0008_admin_source.sql` (new),
`src/agenticml/server/db/workspaces.py`, `src/agenticml/server/webauth.py`,
`src/agenticml/server/app.py`, `src/agenticml/server/up.py`,
`src/agenticml/cli.py`, tests.

1. **Migration 0008**:
   `ALTER TABLE accounts ADD COLUMN server_admin_source TEXT CHECK
   (server_admin_source IN ('list','manual'));`
   NULL on existing rows means "not from the list" (kept on removal). Plain
   SQL works on SQLite and Postgres; `accounts` has no `workspace_id`, so no
   RLS work.
2. **`AccountRepo`**:
   - `set_server_admin(login, enabled, *, source='manual', tx=None)`. Opens
     its own write transaction when `tx` is None (current callers keep
     working); always takes `advisory_lock('users')`.
     - Enable: `server_admin=1`. Source: `'manual'` overwrites anything;
       `'list'` is written only when the account was not already a server
       admin (never downgrade a manual grant to list).
     - Disable: refuse with a new `LastServerAdminError(ClientError)`
       ("cannot remove the last server admin") when this account is the only
       row with `server_admin=1`; otherwise `server_admin=0`,
       `server_admin_source=NULL`.
     - Returns the updated row.
   - `list()` also returns `server_admin_source`.
   - `server_admins(tx=None)`: rows with `server_admin=1`, ordered by login.
   - The 2.x conversion path that sets `server_admin=1` for the first owner
     of `default` (`db/repos.py` about line 101) is unchanged (source stays
     NULL = manual).
3. **Configuration**: `--admin-emails LIST` on `server serve` and
   `server up`, env `AGENTICML_SERVER_ADMIN_EMAILS` (flag wins). A helper
   `_admin_emails_from_args(args)` in `cli.py` splits on commas, strips,
   drops empties, lowercases (`str.lower`, as `emails_equal` does). Entries
   that are not `is_email_login` are dropped with a warning naming the bad
   entry (no crash: a typo in a GitHub variable must not take the hosted
   service down). Thread `admin_emails` (a frozenset, default empty)
   through `serve`, `make_server`, `IngestServer.__init__` and
   `WebAuth.__init__`, and through `up.py` (systemd and launchd writers,
   `install_unit`, `up` install and serve extras) the way `open_signup` is.
   In `WebAuth.__init__`: if the list is non-empty and Firebase is off, log a
   warning ("--admin-emails is ignored without --firebase-project") and use
   an empty list. Log the count of admin emails at startup (not the
   addresses).
4. **Sign-in** (`_firebase_auth`). Let
   `listed = email_verified_for_link(claims) and claims.email and
   claims.email.lower() in self.admin_emails`.
   - **Create**: inside the existing write transaction (about line 1180),
     after `_firebase_find_or_claim`, if `account is None and listed`: create
     the account like `_firebase_open_signup` does (same display name rule)
     but with `created_by='admin-emails'`, link the uid, and create **no**
     workspace. If `accounts.get(claims.email)` already exists (not
     claimable, e.g. it has a password), do nothing (the existing
     "no access" answer stays). This runs before the open-sign-up branch, so
     a listed email never gets a personal workspace from this path, and
     works with open sign-up off. Audit `account.create`
     (`actor=login, via="admin-emails"`, detail
     `{"created_by": "admin-emails"}`).
   - **Grant / revoke**: for every resolved account (all three paths, so
     also after invite redemption and uid lookup), inside the second write
     transaction (about line 1221) before the row is re-read:
     - `listed` and not `server_admin`: `set_server_admin(login, True,
       source='list', tx=tx)`; audit `account.server_admin` with detail
       `{"enabled": true, "source": "admin-emails"}`,
       `actor=login, via="admin-emails"`.
     - not `listed`, `server_admin` and source `'list'`: revoke with the
       last-admin guard. If it is the last server admin, keep it, log a
       warning and do not fail the sign-in. Otherwise audit
       `{"enabled": false, "source": "admin-emails"}`.
     - Anything else: no change.
   - The sign-in must not fail because of the list logic except for real
     database errors (which already answer 503 or 500 as today).
5. **CLI**: `accounts add --server-admin` and `accounts set-server-admin`
   pass `source='manual'`; `set-server-admin off` on the last admin now
   fails with "cannot remove the last server admin" (exit 1). `accounts
   list` shows a `source` column (`list`, `manual` or `-`) and JSON gains
   `server_admin_source`.

Tests (new or extended; all must pass on SQLite and Postgres):

- Migration: a database at version 7 with a server admin upgrades; the admin
  keeps `server_admin=1` with NULL source.
- Repo: grant manual/list; list does not downgrade manual; manual upgrades
  list; disable clears source; last admin refused (and the row unchanged);
  works inside a passed transaction.
- Sign-in, Firebase server fixtures from `tests/test_server_firebase.py`:
  - listed verified Google email with no account and open sign-up off →
    200, account `created_by='admin-emails'`, server admin, source `list`,
    no workspace, `/workspaces` shows the Admin link, audits present;
  - same email in different case in the list → works;
  - unverified email (`email_verified=False`) or untrusted provider → not
    created, 403 `no_account`, no grant;
  - listed email that already has a pending account (claimable) → linked
    and granted;
  - listed email that already has a password account → 403, nothing
    granted;
  - existing linked account (by uid) whose email is added to the list →
    granted at sign-in; removed from the list → revoked at next sign-in
    while another admin exists; kept (with warning) when it is the last
    admin;
  - manual admin whose email is not listed → kept;
  - invite redemption by a listed email → membership from the invite and
    server admin;
  - open sign-up on + listed email → account created by the list path
    (`created_by='admin-emails'`), no personal workspace;
  - Firebase off + list → startup warning, list ignored.
- Config: `serve` and `up` receive `admin_emails` from flag and env (copy
  `test_cli_passes_open_signup` and `test_cli_serve_firebase_flags`); bad
  entries dropped with a warning; systemd unit and launchd plist carry
  `--admin-emails`.
- CLI: `set-server-admin off` on the last admin exits 1; `accounts list`
  shows the source.

## 24.7b † `/admin`: server admins and workspaces for new owners (Sonnet)

Files: `src/agenticml/server/routes.py`, `src/agenticml/server/db/workspaces.py`,
`src/agenticml/ui/static/app.js`, `src/agenticml/ui/static/app.css` (only if
needed), tests in `tests/` and `testbed/tests/`.

1. **API** (all `scope="server_admin"`, so non-admins get the same 404 as an
   unknown path; one handler `admin_server_admins` registered in the
   handler table):
   - `GET /api/admin/server-admins` → `{"server_admins": [{login,
     display_name, email, source ("list"|"manual"), firebase (bool),
     pending (bool: no password, identity or firebase_uid), created_at}]}`.
     Lists server admins only (not all accounts; with open sign-up there can
     be many).
   - `POST /api/admin/server-admins` body `{"login": "<email or login>"}`
     (via `read_json`, so CSRF, JSON type and size checks apply): grants
     server admin with `source='manual'`. If no account exists, the login
     is an email (`is_email_login`) and Firebase is on, create a
     credential-less account
     (`created_by=<acting admin login>`) in the same transaction; its first
     verified Firebase sign-in links it. A non-email login with no account →
     404 `{"error": "unknown account"}`. Already a server admin → 200 with
     the row (source becomes `manual`). Responses: 201 when an account was
     created, else 200, body `{"server_admin": {...}, "account_created":
     bool}`. Audits: `account.create` (when created, detail
     `{"pending": true}`) and `account.server_admin` (detail
     `{"enabled": true, "source": "web"}`) through `_server_audit`.
   - `DELETE /api/admin/server-admins/<login>` (CSRF checked as the invites
     DELETE does): revoke with the guard. 404 unknown account or not a
     server admin; 409 `{"error": "cannot remove the last server admin"}`.
     Self-removal is allowed when another admin exists. Audit
     `account.server_admin` `{"enabled": false, "source": "web"}`. Note in
     the response and UI: an email still on `HOSTED_ADMIN_EMAILS` gets
     server admin back at its next sign-in.
   - The login in the path is URL-decoded the same way member routes handle
     `name`; emails are matched case-insensitively (`AccountRepo.get`).
   - Add the three route names to the isolation suite case table
     (`tests/test_server_isolation.py`) and to the route-table tests.
2. **Workspace for a new owner email**: `POST /api/admin/workspaces` keeps
   its body. When `owner` is an email with no account and Firebase is on,
   create a credential-less owner account (`created_by=<acting admin
   login>`) and the workspace in **one** transaction (add a keyword such as
   `create_owner=True` to `WorkspaceRepo.create`, or do both in the route
   inside one `db.transaction(write=True)`); a failed workspace create
   (duplicate slug, bad name) must not leave the account behind. With
   Firebase off, or a non-email owner, keep today's 400 "workspace needs an
   existing owner account". Response adds `"owner_created": bool`. Audit
   `account.create` (`{"pending": true}`) before `workspace.create`, and log
   the lowercased owner login in `workspace.create` (today it logs the raw
   string).
3. **UI** (`adminPage` in `app.js`): a "Server admins" section between the
   workspaces table and Activity: `h2` "Server admins", a table (aria-label
   "Server admins"; columns Login, Source, Sign-in, Actions; `data-label`
   on every cell for the stacked 375px layout) and an "Add server admin"
   button opening a dialog (label "Email or login", button "Add"). Row
   action "Remove" with a confirm dialog that says list emails come back at
   their next sign-in. Show the server's error text on 404/409. Reuse the
   existing helpers (`dialog`, `button`, `chip`, `write`, `showError`) and
   the refresh sequence guards. The "New workspace" dialog keeps its labels
   ("Slug", "Name", "Owner login") and adds a muted hint: "If no account
   exists for this email, one is created; it is linked when they first sign
   in." When the response has `owner_created`, say so in the table refresh
   message or a toast as the page already does for other actions.
4. **Firebase copy on the Team page**: when the session's `auth` is
   `"firebase"`, the invite dialog says "This invite link is shown once.
   They sign in with Google or email and password, using this email; the
   email must be verified." and the per-row "Invite link" dialog says "This
   signs them out and gives them a new sign-in link." Password servers keep
   today's text.

Tests:

- API (`tests/test_server_workspace_routes.py` or a new
  `tests/test_server_admins_web.py`): list; add existing account; add new
  email creates a pending account that a later verified Firebase sign-in

- Workspace create: new owner email → 201, `owner_created`, pending account

- UI (`testbed/tests/test_server_admin_dashboard.py`): the section lists

## Review changes (Nov 13, 2026)

The supervisor review and three read-only review passes changed these points:

- The last-admin guard counts only other server admins that can sign in
  (password, identity or `firebase_uid`). A pending admin does not keep the
  last real admin removable; a pending admin itself can always be removed.
- `POST /api/admin/server-admins` creates a pending account only with
  Firebase on (as workspace create does); otherwise an unknown email is 404.
- A failed store preparation after a workspace create also removes the new
  pending owner account.
- The server-admins API reports `signin` (`firebase`, `identity`, `password`
  or `pending`); removing yourself on `/admin` goes to `/workspaces`.

## Edge cases

- Email case: the list, account logins and claims compare lowercased.
- Unverified email or untrusted provider never matches the list.
- A listed email whose account has a password or identity is not taken
  over.
- The list never removes the last server admin who can sign in; neither
  does `/admin` or the CLI.
- A manual grant to a listed person survives removal from the list.
- Firebase off: list ignored with a warning; `/setup` keeps working.
- An invalid list entry is dropped with a warning, never a crash.
- Concurrency: all grants, revokes, creates and guards run under
  `advisory_lock('users')` inside one transaction.
