# Package 24.13: Phase 6 restore drill and real-EFS benchmark

Nov 16, 2026 · Supervisor plan · Release 3.0 · AWS roadmap Phase 6

## Goal

Run AWS roadmap Phase 6 safely and repeatably:
- **6.1:** restore the hosted service's three stores into isolated drill
  resources and prove the restored service works:
  - RDS, by point-in-time restore;
  - EFS, from AWS Backup;
  - S3 object versions at the recovery time.

Then remove every drill resource and record the results. Phase 5 is done
(Nov 16, 2026, package 24.12).

## What is true today (checked read-only, Nov 16, 2026)

- **No new IAM is needed.**
  - A PITR restore of the Postgres instance keeps the master password as of
    the restore time, and creates no managed secret. The restore time must be
    after the secret's last rotation (Nov 12, 2026). Drill tasks therefore
    reuse the existing execution role, which reads the production secret at
    task start, exactly as the live service does. No person reads the value.
  - The first drill task proves the password carry-over.
- **The drill server needs an S3 principal for the test bucket.** The only
  existing one is the hosted task role, granted access through a bucket
  policy on the drill bucket.
  - That role can also write to the production `hosted/*` prefix.
  - The guards below are the defence: task definitions are generated by a
    script that refuses production identifiers, and the drill entrypoint
    re-checks its environment.
  - A dedicated role is the alternative. It is an IAM create and needs the
    owner's approval.
- **Today's 05:00 UTC daily EFS recovery point is not a consistent cut.**
  The backup ran during Phase 5 syncs. Use an on-demand point (option A)
  or the next scheduled one (option B).
- **The benchmark runs on the restored drill filesystem**, not on production
  EFS. Its settings match production: same KMS key, generalPurpose, elastic,
  TLS mount through an access point. Only IAM mount auth is off, which
  affects authorization, not I/O.
- The image has no `psql`, but has Python and psycopg. ECS Exec is not
  usable from the operator machine (no Session Manager plugin), so every
  check runs as a one-off Fargate task in a separate cluster
  `agenticml-restore-drill`.
- **Cost:** under $1 in total, with resources living 3 to 5 hours (prices
  from the AWS Pricing API, us-east-2).
- **Deadline:** drill tasks must start before the next secret rotation,
  Nov 19, 2026, 23:59 UTC.

## Approach

1. **Scripts.** Start from the staged drafts in the supervisor's scratchpad
   (`p6/`) and rework them:
   - **Discover every ID at run time.** No account number, ARN, subnet,
     security group, filesystem or secret identifier in the repo; read them
     from the `agenticml-hosted` stack outputs, resources and the live task
     definition, and pass the drill's own IDs through `state.env`.
   - **Use names and tags.** Every drill resource is named
     `agenticml-restore-drill*` and tagged `Project=agenticml-restore-drill`.
   - **`mk_td.py` refuses** to write a task definition that contains:
     - the production bucket, filesystem, access point or database host
       (except `dbcheck --prod`, which is read-only);
     - an ECS Exec flag;
     - production DNS or the production target group;
     - any port mapping exposed to the load balancer.

     The bench task gets no task role and no database, S3 or Firebase
     variables. The bench script is embedded with a pinned commit and its
     sha256, checked before it runs.
   - **`drill-run.sh` exits non-zero before starting** if the database host
     does not match `agenticml-restore-drill.`, the objects URL does not
     name a bucket starting with `agenticml-restore-drill-`, or the
     public URL is not loopback.
   - **`copy_versions_at.py`:**
     - picks, per key, the latest version with `LastModified <= T` that is
       not hidden by a delete marker at T;
     - copies it with a sha256 check (the key's last segment is the
       sha256);
     - has a `--dry-run`;
     - never writes to the source bucket.
2. **Tests** (`tests/test_restore_drill.py`, pure Python, no AWS):
   - `mk_td` produces each definition from a fixture production task
     definition with dummy IDs;
   - it refuses each production identifier;
   - the bench definition has no task role and no database, S3 or Firebase
     variables;
   - version selection at T: before and after a delete marker, a key
     created after T, multiple versions;
   - the drill-run guard: `bash` with fake env values exits non-zero for
     production-looking values. Skip this test if bash is not available.
3. **Runbook:** update the README section and `scripts/restore_drill/README.md`.
4. **Execution (supervisor, with the owner's profile, after the owner's
   approval):** follow the order in `scripts/restore_drill/README.md`:
   - preflight;
   - recovery point (option A or B);
   - drill cluster;
   - RDS PITR, EFS restore, S3 copy;
   - gate 1, SQL;
   - gate 2, server check;
   - gate 3, new sync and login;
   - 6.2 benchmark (3 repetitions each of 1 and 8 clients, 4 vCPU / 8 GB);
   - cleanup in dependency order;
   - final listing proving nothing remains and production is unchanged.
5. **Record:**
   - recovery point age and recovery duration per store, and total time;
   - integrity results;
   - any cross-store orphans (recorded, not failures);
   - the benchmark tables in `docs/SERVER.md`;
   - the roadmaps and the public status page, with no AWS identifiers on the
     public page.

## Constraints

- No production writes:
  - no change to the production database, EFS, bucket, delete markers,
    service, target group or DNS;
  - read-only `GetSecretValue` by ECS at task start, as for any production
    task;
  - no human-readable secrets.
- Nothing reachable from the internet. Tasks get a public IPv4 only for
  egress, behind a security group with no new inbound rules.
- Every created resource is tagged and removed; the final listing proves it.
- Abort and clean up if any gate fails. Record the failure in the Backlog.

## Deviations

- **Option B instead of A.** An on-demand EFS backup (`start-backup-job`) was
  refused with AccessDenied ("Insufficient privileges") for the operator's
  `aws login` session (admin, no service control policy, no vault policy);
  restore jobs worked. The drill used the scheduled point. Recorded in the
  Backlog (low).
- **Recovery-point rule changed.** The plan restored the database to the
  recovery point's start. Attempt 1 showed that leaves files newer than the
  database, so the rule is now T_DB = T_S3 = the point's `CompletionDate`
  (runbook and `deploy/aws/README.md` updated). Limit: a sync made during the
  backup window can still leave the database ahead of the files for that run.
- **Benchmark database on local disk.** 3.0 refuses SQLite on a network
  filesystem, and the hosted database is Postgres, not on EFS. The benchmark
  keeps SQLite on the task's local disk; run files, appends and objects are on
  EFS. The numbers cover EFS file I/O, not the Postgres path.
- **`check_db` and `rds.force_ssl`.** The app role cannot read `rds.*`
  parameters, so the check reports "not visible to this role" instead of
  failing. The parameter group check in the RDS step is the proof; the `ssl`
  line shows TLS in use.
- **Restored EFS throughput mode** came back as Bursting; it was switched to
  Elastic on the drill filesystem to match production.
