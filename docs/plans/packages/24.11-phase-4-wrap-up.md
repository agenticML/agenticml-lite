## Facts from the code

- `src/agenticml/sync.py` keeps `runs/<id>/sync.json` as
  `{"version": 1, "hosts": {<host>: state}, "pruned": bool,
  "pruned_hosts": [...]}`. `_host_state`, `_save_state`, `_clear_host_state`
  (`--reset`), `_pruned_upload_block`, `_selected_ids` (`--all`) and
  `_sync_locked` all key it by the server base URL only.
- `/v2/whoami` returns `workspace` (the key's workspace slug) on 3.0 servers
  (`server/ingest.py`); 2.x servers do not.
- A cursor that is empty makes `_sync_locked` ask `/v2/runs/<id>/state` and
  rebuild the cursor from the server (`_recover`), so a fresh per-workspace
  entry costs one request and resends no accepted bytes.
  `client.run_state()` returns None when the run is not in the key's
  workspace.
- `store/gc.py` only reads `hosts.*.complete`, so key names do not matter
  to it.
- Firebase servers: the member re-invite (`POST /api/w/<slug>/members/<login>/invite`
  → `userspage.handle` → `UserRepo.create_invite`) clears the account's
  password, signs it out and stores a token in the `invites` table, which the
  Firebase invite page accepts for an email login. For an account that is
  also a member of another workspace the request answers 403
  (`_reject_cross_workspace_credentials`); with open sign-up on, everyone
  who signed up on their own owns a personal workspace, so that is most
  members. The link adds nothing on Firebase: an email account with no
  Firebase link is claimed on its first verified sign-in at `/login`, and a
  linked one just signs in; Remove still signs a member out.

### 24.11b: sync state per workspace

1. New key: `_state_key(host, workspace)` returns `host` when `workspace` is
   None (2.x servers, dry runs) and `f"{host}/w/{workspace}"` otherwise (the
   same path as the workspace dashboard).
2. `_sync_locked`: compute the key from `_identity(client)["workspace"]`
   (dry run: see 5); use it for load, save and the pruned-upload check.
3. Migration (non-dry-run, under the run lock): when the key has no entry,
   `key != host`, and a protocol-2 entry exists under the bare `host`, ask
   `client.run_state(run_id)`. If the server has the run in this workspace and
   `_check_owner` passes, move the entry to the new key (removing the bare
   entry) with `complete=False`, so this pass re-commits and the server
   verifies the sizes. Otherwise start a fresh entry and keep the bare one
   for the workspace that has the run.
4. Pruned runs: `_pruned_upload_block` already blocks when another key is in
   `pruned_hosts` or has `pruned` set; with per-workspace keys a run pruned
   after syncing to workspace A is refused for workspace B, as it should be.
   Show the key in the message (`https://host/w/a`).
5. `--dry-run` (no client, no identity): use the only entry for this host if
   there is exactly one (bare or `/w/`), else an empty state.
6. `--all` (`_selected_ids`) and `--follow`: pass the identity's workspace,
   so idle checks read the per-workspace entry. A run with only a bare entry
   is selected once and migrated by step 3.
7. `--reset RUN_ID`: drop the bare entry and every `host/w/*` entry for that
   host (no network needed; the next sync recovers from `/state`).

## Constraints

- No change to the server protocol or to `sync.json`'s version: old clients
  ignore unknown host keys, and 2.x servers keep the bare-host key.
- No new dependencies; Python 3.9 compatible.
- Dashboard: no horizontal overflow at 375px.

## Edge cases

- The same run synced to two workspaces with two keys from one store: both
  receive it, each with its own cursor.
- Old store with a complete bare entry, synced with a key for the same
  workspace: adopted, nothing resent, one commit.
- Old bare entry, key for another workspace where the run is absent: full
  upload there, bare entry kept.
- Old bare entry, remote owned by another user in this workspace:
  `OwnershipError` as today; nothing saved under the new key.
- 2.x server (no `workspace` in whoami): bare key, unchanged behaviour.
- Pruned run synced to A, then synced to B: refused with the pruned message.
